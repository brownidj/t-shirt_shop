# Responsive T-shirt Preview Grid

## Purpose and scope

This guide describes the future multi-preview gallery for T-shirts on a
catalogue page. It does **not** change the current product-detail UI: that
page deliberately shows one selected preview in `#variant-panel`, below the
main design image. Use this pattern only when a page needs to show a collection
of T-shirt previews.

Keep the implementation in the existing Django/Oscar catalogue structure:

- Template: `templates/oscar/catalogue/detail.html`, or the relevant catalogue
  template for the new gallery.
- Page-specific CSS: the template's existing `{% block extrastyles %}` block;
  move it to a project stylesheet only if it becomes shared by more than one
  page.
- Dynamic preview source: retain the current `tshirt_preview` URL convention
  already used by the product-detail JavaScript. The renderer, style assets,
  and colour lookup remain server-side concerns; this grid only lays out the
  returned images.

Do not duplicate `id="variant-panel-image"`. It belongs to the current single
selected-preview panel. A multi-preview gallery must use classes and, where
selection is needed, `data-*` attributes.

## Recommended responsive policy

Use three content-oriented ranges:

| Range | Viewport width | Columns | Why |
| --- | ---: | ---: | --- |
| Phone | below `640px` | 1 | A full-width card keeps the shirt and its detail legible. |
| Tablet / small laptop | `640px` to `1023.98px` | 2 | Two cards retain useful image size without a cramped third or fourth column. |
| Desktop | `1024px` and wider | 4 | Four cards fit comfortably in a typical modern desktop content container. |

These are deliberately not device-brand breakpoints. The change at `640px` is
where two preview cards stop being comfortably useful; the change at `1024px`
is where four cards become reliable in the page container. They also sit
cleanly beside the existing Bootstrap-style `col-md-*` layout without requiring
Bootstrap row or column classes for each preview card.

### Is 375px unnecessarily small?

`375px` should not be a breakpoint or the primary design target for a
new-device-only brief. Current mainstream phones commonly present a CSS
viewport around `390px` or `430px`; `375px` is mostly an older iPhone width.
The practical primary checks are therefore `390px` and `430px`.

Still, do not deliberately exclude `375px` (or `360px`, which remains common
on Android). The one-column rules require no special work at those widths, and
checking that they do not overflow is a cheap resilience check. The important
point is that the layout changes at `640px`, not at an arbitrary `375px` line.

## Template structure

Put every preview card inside one grid container. Replace `previews` and its
fields with the collection supplied by the eventual catalogue view.

```django
<section class="tshirt-preview-grid" aria-label="T-shirt previews">
    {% for preview in previews %}
        <article class="tshirt-preview-card">
            <img
                class="tshirt-preview-card__image"
                src="{{ preview.image_url }}"
                alt="{{ preview.name }} T-shirt preview"
                loading="lazy">
            <h3 class="tshirt-preview-card__title">{{ preview.name }}</h3>
        </article>
    {% endfor %}
</section>
```

For previews rendered by the existing endpoint, form `preview.image_url` using
the same URL and query-string values currently assigned to
`#variant-panel-image` in `detail.html`. Preserve URL encoding for the style
and colour values. Do not make the image source depend on a static preview
file: dynamic rendering is intentional because a parent design image can
change.

If gallery cards are interactive, add a button inside each card or make the
card's existing action an accessible link. Do not attach identical IDs to cards
generated by the loop.

## CSS

Add the following inside the existing `extrastyles` block while this gallery is
page-specific. The grid is mobile-first: one column is the base rule, so narrow
screens remain safe even if a media query is unavailable or overridden.

```css
.tshirt-preview-grid {
    display: grid;
    grid-template-columns: minmax(0, 1fr);
    gap: 1rem;
}

.tshirt-preview-card {
    min-width: 0;
    padding: 1rem;
    border: 1px solid #dee2e6;
    border-radius: .25rem;
    background: #fff;
}

.tshirt-preview-card__image {
    display: block;
    width: 100%;
    height: auto;
    object-fit: contain;
}

.tshirt-preview-card__title {
    margin: .75rem 0 0;
    font-size: 1rem;
}

/* Tablet / small laptop: two previews per row. */
@media (min-width: 640px) {
    .tshirt-preview-grid {
        grid-template-columns: repeat(2, minmax(0, 1fr));
    }
}

/* Desktop: four previews per row. */
@media (min-width: 1024px) {
    .tshirt-preview-grid {
        grid-template-columns: repeat(4, minmax(0, 1fr));
    }
}
```

`minmax(0, 1fr)` is required rather than plain `1fr`: it lets a track shrink
when a generated image, long name, or other child has a large intrinsic width.
Together with `min-width: 0` on the card and `width: 100%` on the image, it
prevents horizontal page scrolling while preserving image aspect ratio.

Avoid fixed card widths, `float` layouts, and a Bootstrap `.row` with manually
chosen `.col-*` classes. CSS Grid expresses the actual requirement directly:
all cards share the available row width and reflow as a single collection.

## Implementation sequence

1. Add the gallery markup to the catalogue template that supplies multiple
   previews; leave the existing selected-preview panel unchanged.
2. Add the scoped CSS above to that template's `extrastyles` block.
3. Connect each image to the existing dynamic preview URL generation, keeping
   style and colour query values URL-encoded.
4. If cards can change the selected variant, use classes or `data-*` values to
   find the card; continue using the one existing `#variant-panel-image` only
   for the selected-preview panel.
5. Test with actual dynamically rendered images, including both a pale and a
   dark garment colour. Image rendering quality is outside this layout work,
   but it can expose intrinsic-size or loading-state problems.

## Verification checklist

Check the gallery in browser responsive mode at these viewport widths:

| Width | Expected result |
| ---: | --- |
| `390px` | One full-width card per row; primary modern-phone check. |
| `430px` | One full-width card per row; larger modern-phone check. |
| `640px` | Two cards per row; breakpoint boundary. |
| `768px` | Two cards per row; typical tablet check. |
| `1024px` | Four cards per row; desktop breakpoint boundary. |
| `1280px` | Four cards per row with even gaps. |

Also make a quick non-blocking check at `360px` or `375px`: it should remain
one column with no horizontal scroll, but it is not the primary design width.
At every width, verify a long product name, a slow-loading image, keyboard
focus (if cards are interactive), and an image with an unusual aspect ratio.
There must be no clipped cards, stretched T-shirts, repeated IDs, or page
overflow.

## Out of scope

This guide does not alter the dynamic renderer in `topository_01/views.py`,
the `tshirt_preview` route ordering, Oscar product attributes, generated
base/mask assets, or the existing single-preview variant-selection UI. Those
areas remain as documented in `TSHIRT_PREVIEW_CURRENT_STATE.md`.
